# 格式与代码组织

> 代码格式关乎沟通，而沟通是专业开发者的头等大事。今天写的功能几个月后可能面目全非，但代码风格会传递"这个系统由一群在乎它的人维护着"的信号。
>
> 具体的空格、换行规则交给格式化工具（lint / prettier / gofmt 等）自动执行。本规范只谈工具无法替你决定的**结构**。

**何时阅读：** 组织文件结构、调整函数顺序或新建源文件时。空格与换行仍交给格式化工具。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 垂直方向

### 1.1 向报纸学习

源文件应当像报刊文章：顶部给出高层次概念与摘要（类名、文档注释），向下逐渐展开细节，直到最底层的函数与实现细节。读者能自顶向下停止于任何一层。

### 1.2 垂直密度表达关联

空行是视觉的段落分隔：

- 每个思想（每组声明、每个逻辑步骤）之间用空行隔开；
- 紧密相关的行保持紧挨——不留空行。如下例中两个 `assert` 各自成组、组内紧凑：

```text
public void shouldRespondToHTML() {
    givenPage("testHtml");
    ...
}
```

### 1.3 垂直距离：关系密切的概念放在一起

- **变量声明**：靠近其使用处；局部变量在函数顶部出现即可。
- **实例变量**：集中放在一处（语言的惯例位置：Java 在类头，C++ 在底部），被多个方法理解时必须容易找到。
- **相关函数**：调用者与被调用者垂直靠近。被调函数放在调者**下方**，让阅读像顺着故事往下走。
- 间接关系（如一个常量只服务于一个方法）也应尽量让定义和使用靠近。

### 1.4 文件大小

- 单文件超过约 200 行多数情况下已经偏大；超过 500 行应视为明确的拆分信号（语言差异可放宽，但同项目内标准要统一）。

## 2. 水平方向

- 一行的合理上限：**80~120 字符**。超出通常是嵌套层级或参数过多的信号，先重构再换行。
- 运算符前后加空格以突出优先级分组：

```text
// 好
int lineSize = lineHeight * lineCount;

// 歧义重排时，空格帮助我们看见结合性
return (-b + Math.sqrt(b*b - 4*a*c)) / (2*a);
```

- 赋值对齐等花式排版会制造虚假结构，且每次增删一行都要求全块重新对齐——不值得。

## 3. 缩进体现层级

- 缩进是唯一廉价的结构可视化手段。即使短小的 `if` 或空函数体也遵守缩进规则，不要把语句挤到一行。
- 循环体、条件体、函数体各退一层；子模块的组织也要在目录上有所体现（这是缩进的"包级版本"）。

## 4. 团队规则

> 一队程序员一致认同一种格式风格：团队成员贡献的代码看起来应该像出自同一个人之手。

- 新成员加入时服从项目现有风格，而不是带来自己的偏好；
- 把团队约定固化到 lint 配置里提交到仓库，让机器执行约定；
- 不评论纯粹的格式问题（那是工具的事），评审火力集中在结构与命名上。
