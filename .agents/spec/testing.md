# 测试

> 测试是让我们敢于重构的保险绳，也是设计质量的反馈机制。脏测试 ≈ 没测试：边际成本随时间上升，最终被删除。
>
> 记住：**测试代码与生产代码同等重要**——它需要被设计、维护、重构。

**何时阅读：** 编写、修改或评审测试时；重构前确认保护网时。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. TDD 三定律

1. 在编写不能通过的单元测试前，不要编写生产代码；
2. 只编写刚好足以失败的测试（编译失败也算失败）；
3. 只编写刚好足以让当前失败测试通过的生产代码。

三定律把工作循环压缩到秒级：红 → 绿 → 重构，让设计与验证始终同步。

## 2. 保持测试整洁

- 测试代码和生产代码一样需要同一套整洁标准：有意义的命名、短小函数、清晰的抽象。
- 反面案例：粗制滥造的测试让人只能"再塞一条"而不是整理既有断言，最后整个测试文件变成无人敢动的泥潭，最终沦于被弃。

## 3. 整洁测试的三段式：Build–Operate–Check

```text
// Build：构造测试数据与环境
makePageWithContent("TestPage", "test content");
submitPage("TestPage");

// Operate：执行被测行为
response = requestPage("TestPage");

// Check：验证结果
assertContains(response, "test content");
```

- 每个测试一个关注点；一个测试函数里堆积多个断言链是对读者的暴击；
- 大量的 arrange 噪音可以下沉到辅助函数 / 建造者方法里：

```text
// 差：断言淹没在搭建代码里
// 好：
assertEquals("not-found", getResponseForNonExistentPage().type());
```

## 4. 领域特定测试语言（DSL）

用一组建模领域的辅助函数（`givenPage` / `submitPage`）包裹实现细节。它不是分层复杂的装饰，而是**把测试意图和实现细节分开**的手段——实现换血时只改一层。

## 5. 双重标准原则

测试环境中的某些简化是允许的，而在生产代码中则不允许：

- 测试中可以用简化的假对象直接放数据，不一定要完整封装或事务保护;
- 但"可读性"的要求两边完全一致——测试比生产代码更依赖读起来一目了然。

## 6. 每个测试一个断言（精神重于形式）

规则的精神：每个测试函数应当聚焦一个概念、回答一个问题。"物理上一个 assert"不必强求，多个 `assert` 组合表达同一个概念、放在同一个辅助断言函数里，也是整洁的。

## 7. F.I.R.S.T. —— 好测试的五要素

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| **F**ast | 快速 | 测试应该快到随手就能跑。慢了就不会频繁运行，就不敢改代码 |
| **I**ndependent | 独立 | 测试之间互不依赖，可以任意顺序单独运行 |
| **R**epeatable | 可重复 | 任何环境下都应得到相同结果（本地、CI、无网络均可） |
| **S**elf-validating | 自足验证 | 有明确的通过/失败输出，不需要人肉比对日志 |
| **T**imely | 及时 | 单元测试应在使其通过的生产代码之前或同时编写 |

## 8. 测试金字塔的最低层纪律

- **单元测试为主**：快、隔离、定位问题精准；上层集成/端到端测试负责跨模块契约；
- 所有外部副作用（网络、数据库、时钟、随机数）在单元测试中注入替身；
- CI 必须跑测试；红灯禁止合入——这是"重构自由度"的制度保障。

## 自查清单

- [ ] 这个测试的名字能不能描述它的行为？（should... when...）
- [ ] 跑一遍全部测试要多久？超过分钟级了吗？
- [ ] 删掉某条测试会影响其他测试吗？
- [ ] 失败信息能直接定位到问题吗？
- [ ] 我是在修复后先补了测试，还是让它裸奔？
