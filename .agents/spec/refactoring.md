# 重构与代码坏味道

> **重构（Refactoring）**：在不改变软件可观察行为的前提下，调整其内部结构，以提高可理解性、降低修改成本。
>
> 重构的核心经济逻辑：设计不是一次付清的成本，而是持续摊销的开销。**让修改越来越容易**，是重构存在的理由。

**何时阅读：** 改既有结构、识别坏味道，或加功能前铺路时。加功能与重构不同时做、不塞进同一次提交。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 两条顶帽子

同一时刻，你只戴一顶帽子：

- 添加新功能：只管加测试、加代码；
- 重构：只移动/调整代码，不加任何功能、不改任何行为。

两顶帽子频繁切换没问题，但**绝不同时干两件事**。每次提交要么是功能提交，要么是纯重构提交。

## 2. 三次法则

> 事不过三，三则重构。

第一次做某件事：直接写；第二次做类似的事：皱眉但可以复制；第三次再做同样的事：重构。

## 3. 什么时候重构

| 场景 | 做法 |
| --- | --- |
| 预备性重构 | 要加功能前，先把相关部分整理得"容易加"——花几分钟铺路能省一小时绕路 |
| 增进理解的重构 | 读不懂某段代码时顺手重命名/提函数，把理解固化进代码 |
| 捡垃圾式重构 | 路过时看见垃圾（命名烂、重复），修掉它。遵守童子军军规 |
| 评审讨论中 | 讨论到"如果这样就好了"，当下就是实施时机 |

### 什么时候停下来

- 接近截止时间、上下文不允许时的自我克制；
- 代码能跑、且只是"我不喜欢这种写法"——不算理由；
- 烂到核心、补丁摞补丁的模块：评估**重写**是否比重构便宜（这已经不是重构范畴）。

## 4. 重构的基本工作流

```
1. 确认有一组可靠的测试                ← 没有就先补
2. 做一次极小的结构变动（一个手法）
3. 运行测试 → 全绿
4. 提交本次小改动
5. 重复 2~4
```

铁律：

- **小步快跑**：每次只做一个手法、几行代码的量级。步子越小，出错越快发现、回滚越便宜。
- **机器保证等价**：不靠"我觉得没改坏"——靠测试与类型检查兜底。
- 重构序列中的中间态允许存在（比如先造出新函数再移走旧调用方），但要在一个短工作循环内收敛。

## 5. 代码坏味道目录

坏味道是表象，背后的病因才是选手法的依据。以下按常见度排序。

### 5.1 神秘命名（Mysterious Name）

改名是最基础的重构。名字改好了，后面一半的问题会自己浮出水面。
→ 手法：改名函数 / 改名变量 / 改名字段。

### 5.2 重复代码（Duplicated Code）

最容易 smelled 的味道。同一段逻辑出现 N 次，就要承担"改一处漏 N-1 处"的风险。
→ 手法：提炼函数（多数情况）、上移到父类、提炼模块。

### 5.3 过长函数（Long Function）

函数越长越难理解。应积极分解的信号包括注释（注释处往往可以提出一个函数）、条件与循环体。
→ 手法：提炼函数；用查询取代临时变量；以卫语句取代嵌套条件；分解条件表达式。

### 5.4 过长参数列表（Long Parameter List）

参数列表越长，数据关系越混乱、调用越难写对。
→ 手法：以查询取代参数；引入参数对象；保留对象整体传参；合并成类（把散落的相关参数与操作它们的行为收拢成一个实体）。

### 5.5 可变数据（Mutable Data）

共享的可变状态是一切诡异 bug 的温床。尽量缩小其作用域：能 local 不 global，能 const 不 let，能用不可变值传递就不就地修改。
→ 手法：封装变量（统一读写入口）；拆分变量（一个变量一个用途）；以查询取代变量；将查询与修改分离。

### 5.6 发散式变化（Divergent Change）与霰弹式修改（Shotgun Surgery）

一对互为镜像的味道：

- **发散式变化**：一个模块因为多种不相干的原因被反复修改 → 应该拆分（提取类/模块），每种变化一个家；
- **霰弹式修改**：一个小改动需要同时触碰很多文件 → 散落各处的逻辑应该收拢（内联、搬移函数、搬移字段）。

两者都指向同一件事：**每个变化原因应当只有一个聚集点**（单一职责原则在模块层的体现）。

### 5.7 依恋情结（Feature Envy）

一个函数大量访问别的对象的数据（`customer.getBillingPlan()...` 反复访问别人），说明它生错了地方。
→ 手法：搬移函数到数据所在的对象。例外的情形是策略、visitor 等模式——它们天生要去关心别人的数据。

### 5.8 数据泥团（Data Clumps）

总是抱团出现的字段/参数（`x,y`、`street,city,zip`）是提取类的信号。
→ 手法：提炼类、引入参数对象、保持对象完整。

### 5.9 基本类型偏执（Primitive Obsession）

满地的裸 `string`/`int`，用约定而非类型承载语义（手机号是 string？金额是 number？）。
→ 手法：以对象取代基本类型（Value Object）、以类取代类型码、以子类取代类型码。

### 5.10 重复 switch（Repeated Switches）

同一个 type 判断在多个地方重复出现——新增一种 type 就要找齐所有 switch。
→ 手法：以多态取代条件表达式；或建立统一的映射表收口。

### 5.11 循环语句（Loops）

当代语言有管道操作（map/filter/reduce）后，手写循环混做"过滤+映射+累加"三件事，可用链式表达替代，更接近意图。（语言没有一等集合支持时可放宽。）

### 5.12 冗赘元素（Lazy Element）

不再被使用的类、函数、只有一层转发的委托、纯标签性父类。
→ 手法：内联函数/内联类、折叠继承体系、删除死代码。

### 5.13 夸夸其谈通用性（Speculative Generality）

"以后也许用得上"的抽象层、参数、分支。事实是：未来往往不会来，而维护成本现在就付。
→ 手法：删掉只用一次的抽象、折叠不必要的层级、移除无人使用的参数。（YAGNI 原则。）

### 5.14 临时字段（Temporary Field）

仅为某种特殊情况设置的实例变量，平时大多为空——理解困难、易生 bug。
→ 手法：提炼类，把临时字段的逻辑封进那个类；为 null 的字段换成特例对象。

### 5.15 中间人（Middle Man）与消息链（Message Chains)

- 消息链：`a.getB().getC().getD().doSomething()`，耦合了链条每一节的结构变化；
- 中间人：类的接口大半只是转发给别人。

两者的平衡点是封装：适度隐藏委托，但当委托层开始变成纯转发时及时"打穿"中间人。
→ 手法：隐藏委托关系 vs 移除中间人，视哪边更痛反复权衡。

### 5.16 异曲同工的类（Alternative Classes with Different Interfaces）

两个类做着几乎一样的事、却顶着不同的方法名。
→ 手法：改名、搬移函数，向同一接口靠拢；差异实在小时考虑合并。

### 5.17 不完善的库类（Incomplete Library Class）

第三方库缺个想要的行为。
→ 手法：引入本地扩展（子类或包装器）加行为；不要为了少一次跳转去改公共内部实现。

### 5.18 数据类（Data Class）

只有字段和取值器的类。多半意味着有其他类在"依恋"它的数据。健康方向是让它逐步获得自己的行为：
→ 手法：把使用这些数据的函数搬进来；封装集合字段（暴露的不是可变列表本身，而是 add/remove/count 等操作）。

### 5.19 被拒绝的遗赠（Refused Bequest）

子类继承了它不需要也不该有的父类成员。
→ 手法：压平继承（以委托/组合取代子类）、推下/拉上成员重新划分职责。

### 5.20 注释（Comments）

最好的注释是把"想解释的逻辑"直接重构成可读的代码。当你正想写一句 "解释一下这里干嘛" 时——那是提炼函数的提示音。
→ 见 [comments.md](./comments.md)。

## 6. 坏味道 → 手法速查表

| 坏味道 | 首选手法 |
| --- | --- |
| 神秘命名 | 改名 |
| 重复代码 | 提炼函数 / 上移 |
| 过长函数 | 提炼函数、卫语句、分解条件 |
| 过长参数列表 | 参数对象、以查询取代参数 |
| 发散式变化 | 提炼类、搬移函数 |
| 霰弹式修改 | 内联、搬移聚拢 |
| 依恋情结 | 搬移函数 |
| 数据泥团 | 提炼类、参数对象 |
| 基本类型偏执 | 引入值对象 |
| 重复 switch | 以多态取代条件 |
| 冗赘元素 | 内联、删除 |
| 夸夸其谈通用性 | 删除抽象 |
| 注释冲动 | 提炼函数 |

## 7. 生成代码

生成的代码与手写代码适用同一套规范；**"能跑"不是验收标准**。大块生成后先按本文识别坏味道并小步重构，再进入下一任务。何时打开哪份规范，见仓库根目录 [AGENTS.md](../../AGENTS.md)。
