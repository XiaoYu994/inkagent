# 数据结构与抽象

> 代码有两类元素：暴露行为、隐藏细节的**对象**；与暴露数据、没有明显行为的**数据结构**。两者都是正当的，但适用于不同场景，且互为反面。

**何时阅读：** 设计类型与模块边界、封装数据、接入第三方库，或出现链式 `.get().get()` 时。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 数据抽象

- 不要仅凭"有 getter/setter"就认为实现了抽象。真正的抽象是**以抽象的方式表述数据**，让实现细节藏在接口后面。

```text
// 差：实现暴露——调用方知道这是直角坐标
double x = point.getX();
double y = point.getY();

// 好：接口是抽象的，实现可以自由切换
double distance = point.getDistance(target);
```

```text
// 差：把内部表示直接兜售出去
public class VehicleFuelGauge {
    public double getGallonsOfGasoline() { ... }
}

// 好：表述的是抽象（油量百分比），而不是存储格式
public double getPercentOfTankFull() { ... }
```

## 2. 对象与数据结构的反对称性

两者提供相反的能力：

| | 添加新类型 | 添加新函数 |
| --- | --- | --- |
| **面向对象**（类 + 多态） | 容易：新增子类即可，不动现有代码 | 困难：要改所有类 |
| **过程式**（数据结构 + 函数） | 困难：要改所有函数 | 容易：加个新函数即可 |

因此选择依据是**系统未来最常发生的变化方向**：

- 未来要频繁加新类型 → 用对象/多态；
- 未来要频繁加新操作 → 用数据结构 + 过程式代码；
- 聪明的程序猿知道什么都想不变是不可能的，所以需要针对预期变化做选型，并且这两者可以按模块混用。

警惕"半吊子混合体"：既有公共字段又有业务方法、既想要多态又偷懒暴露数据——它让添加两种东西都变难。避免这种结构。

## 3. 得墨忒耳律（Law of Demeter）

模块不应了解其所操作对象的内部情形。方法 `f` 只应调用以下对象的"朋友"：

1. `f` 所属的类自身的方法与字段；
2. `f` 的参数对象；
3. `f` 内创建的对象；
4. `f` 直接持有的组件实例。

违反形态是"火车残骸"式的链式取值：

```text
// 差：知道了中间三层的内部结构
final String outputDir = ctxt.getOptions().getScratchDir().getAbsolutePath();

// 好1：只和朋友说话
BufferedOutputStream bos = ctxt.createScratchFileStream(classFileName);

// 好2：如果这就是一串纯粹的数据容器（无行为的结构），链式访问可以接受
```

最后一条很重要：对**数据结构**（DTO）而言没有得墨忒耳问题；这条规则约束的是**对象**。混淆二者的边界时最容易出现错误应用。

## 4. DTO 与边界处的简单结构

- 在进程内外、跨网络传输数据时使用无行为的数据传送对象（DTO），通常包含序列化逻辑；
- 借助代码生成或序列化库省去手写模板代码；
- 不要把 ORM 生成的对象、第三方客户端返回的结构体一路传递到业务核心——在边界处转换成自己的领域模型（见下一节）。

## 5. 边界（Boundary）：守住第三方代码

### 5.1 不泄漏第三方类型

对外部 API / SDK 的类型设防，用适配器或包装层包住它们：

```text
// 差：Map 类型散落在整个调用链里，键值约定无人保证
Map<Sensor, Location> sensors = ...;
Sensor s = sensors.get(sensorId);

// 好：封装成领域语义的容器
Sensors sensors = ...;          // 内部怎么存由它决定
Sensor s = sensors.getById(sensorId);
```

包装层带来的额外好处：当第三方升级、换实现、改签名时，系统只有一处需要改动。

### 5.2 学习性测试（Learning Tests）

接入任何第三方库时，先写一组小测试来验证"我对它行为的理解"：

- 免费：成本几乎为零、随手可写；
- 精确验证 API 在当前版本的行为，而不是靠文档猜测；
- 第三方库发布新版后，跑一遍学习测试即知是否有破坏性变更；
- 这也是探索性重构前的安全网来源之一。

### 5.3 使用尚不存在的代码

边界内侧一侧定义"我想要的接口"，先用假实现推进开发，等外部依赖就绪后再替换为适配器。这能让团队并行、也让外部依赖保持可替换。

## 6. 系统层面的整洁（要点）

- **构造与使用分离**：构造逻辑放在 `main` 或组合根中，日常代码路径假设一切已就绪。
- **依赖注入（DI）**：对象不自己 new 出协作者，而是接受注入；这同时是可测试性的来源。
- **延迟决策**：不需要现在就确定的横切机制（缓存、事务、日志）不提前铺管道；推迟到最后切实用的时刻。
- **关注点分离**：一个模块只回应一类变更（见 [refactoring.md](./refactoring.md) 的"发散式变化"）。
