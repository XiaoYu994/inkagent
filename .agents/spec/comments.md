# 注释

> "别给糟糕的代码加注释——重新写吧。" —— Brian Kernighan & P.J. Plauger
>
> 注释的存在是失败的声明：我们无法用代码表达自己，才退化到用注释。注释会撒谎（因为它们不能跟着代码自动更新），而代码不会。

**何时阅读：** 打算写注释、文档字符串或删除注释之前；评审注释时。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

**第一原则：与其花时间写解释性注释，不如花时间把代码清理干净。**

唯一真正好的注释，是你想办法不去写的注释。但这不等于"禁止注释"。以下是分类清单。

## 好注释

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 法律信息 | 许可证、版权头（尽量用约定/配置简化，而非粘贴大段协议文本） | 文件头的 license 声明 |
| 提供信息的注释 | 补充无法从代码读出的背景，如正则的含义 | `// 匹配消耗时间在 700~1000ms 的行` |
| 对意图的解释 | 解释"为什么"，而不是"做了什么" | `// 这里多线程不安全，但上游已保证单线程调用` |
| 阐释 | 把晦涩的返回值或参数翻译成更易读的形式——前提是有验证价值 | `assertTrue(a.compareTo(a) == 0, "a == a");` |
| 警示（Warning） | 提醒别人某个决定背后的代价 | `// 不要运行此测试，它要跑 9.5 分钟` |
| TODO | 记录当前该做而未做的事项——但不是随手丢弃烂代码的借口 | `// TODO: 依赖下发后补上真实校验` |
| 放大 | 把某处看似过度谨慎或丑陋、实则重要的地方放大强调 | `// 若去掉 trim()，行尾空格会让匹配失败` |

## 坏注释

大多数注释都属于以下几类。写注释前先对照：

- **喃喃自语**：只有作者自己看得懂；读者找不到上下文就无法理解。
- **多余的注释**：代码本身已经说清了事（`i++; // i 加一`）。读代码比读注释还慢时，注释就是负资产。
- **误导性注释**：注释与代码行为不符——多半是改了代码忘改注释。
- **循规蹈矩式注释**：规定每个函数都要有 Javadoc 的教条产物。模板化填充的注释是废话注释的批量生产。
- **日志式注释**："2024-03-02 张三修改了……"——这是版本控制系统的职责。
- **所有权签名**：`/* 作者: 李四 */` ——同样是版本控制系统的职责。
- **废话注释**：无新信息且措辞错误的注释；最糟糕的是复制粘贴产生的错字版本。
- **可用函数或变量替代的注释**：

```text
// 差
if (employee.flags & HOURLY_FLAG) ...

// 好
if (employee.isEligibleForFullBenefits()) ...
```

- **位置标记**：`//// Actions ////` 这类横幅。少量使用可整理结构，滥用只会堆垃圾。
- **闭合括号后的注释**：说明这个 `while` 是干什么的——说明函数太长了，先拆函数。
- **注掉的代码**：注掉的代码就是坟墓，没人敢删它。交给版本控制。
- **HTML 注释**：编辑器和阅读器都解析不了你精心排版的 `<b>` 标签。
- **非本地信息**：描述离注释很远的系统细节的注释不可信。
- **信息过多**：把 RFC 或论文粘进注释里不会让读者变聪明，给出出处链接即可。

## Javadoc / API 文档注释

公共 API 值得写文档注释，否则就别写。写的时候关注：

- 参数与返回值的契约（什么时候会抛异常、副作用是什么）；
- 例子比长篇描述更有价值；
- 如果一条 API 文档注释需要大段补充解释——这往往在提示 API 本身的抽象有问题。

## 自查清单

- [ ] 我写的这条注释能否通过改名、提函数、删废码来代替？
- [ ] 它说的是"为什么"，还是复述了"做了什么"？
- [ ] 一年后代码被改动时，有人能看到并同步更新这条注释吗？
- [ ] 有没有更好的办法直接表达这段逻辑？
