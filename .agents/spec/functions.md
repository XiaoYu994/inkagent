# 函数与方法

> 函数是程序中第一层复用与抽象的单元。所有规范中，函数规则对可读性的影响最直接。

**何时阅读：** 编写、修改、拆分或评审函数/方法之前。加载协议见仓库根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 短小

- 经验值：一个屏幕能放下；超过约 20 行应当反思是否在一件以上的事。
- `if` / `else` / `while` 语句内的代码块应只有一行——通常是一个函数调用。这既保持函数短小，又给块内调用起了文档作用。
- 缩进层级不应超过两层。

## 2. 只做一件事

**判断标准：**

- 能否从函数中再提出一个函数，且新名字不是对原函数的简单复述？能 → 原函数做了不止一件事。
- 函数体内是否存在多个可分辨的"段落"（不同抽象层次的内容）？

```text
// 反例：名字说 includeSetupsAndTeardowns，实际却做了计算+判断+包含三件事
boolean includeSetupPage() { ... }

// 改造后每层只做一件事
runTestCases → setUp → invokeTest → tearDown
```

## 3. 每个函数一个抽象层级

自顶向下读代码时，函数体里出现的操作应该处于**同一**抽象层级：

```text
// 高层级抽象：业务流程
renderPageWithSetOfErrors() {
    if (isTestable(page)) ...
}

// 低层级实现不应混进来：
append("\n"); pathName.append("/");  // 这是字符串操作层级
```

确保自顶向下的阅读叙事："要做 A，先做 B；做 B 要先做 C……"。每个函数后面紧跟着下一层级的函数。

## 4. switch 语句的处理

switch 天生要做多件事且容易到处重复：

- 出现一次、埋藏在低层级（如工厂方法内部）、用于创建多态对象——可以容忍；
- 在多处对同一个类型做 switch → 提取为多态（以子类/策略取代条件分支）。

## 5. 使用描述性的名字

- 长而具描述性的名字 **优于** 短而费解的名字，更优于描述性的长注释。
- 命名风格保持一致：`setupTeardownInclude` 与 `includeSetupAndTeardownPages` 是两种思路，选一种贯彻。
- 别害怕重命名。改名是改善可读性的杠杆，找不到好名字往往说明函数职责有问题——先重构，再命名。

## 6. 参数越少越好

理想参数个数：零 > 一 > 二，三元尽量避免，四元以上几乎总要重构。

| 情形 | 手法 |
| --- | --- |
| 二元函数的两参数属于同一概念 | 合并为对象（`x, y` → `Point`） |
| 一个参数来自接收者自身 | 改成成员/字段调用 |
| 一元参数只是标记开关 | 拆成两个函数（见下节） |
| 同一组参数反复一起出现 | 引入参数对象 |

函数名要与参数呼应，形成"动词—名词"的小句子：`assertExpectedEqualsActual(expected, actual)`。

## 7. 不要使用标识参数

传布尔值的函数宣布了自己做不止一件事：

```text
// 差：true/false 走两条路径
render(true);

// 好：拆开
renderForSuite();
renderForSingleFailure();
```

## 8. 避免输出参数

输出参数违反直觉——我们期望参数是"输入"，返回是"输出"。

```text
// 差：调用者以为 appendFooter(s) 把 s 加进去，实际上改了 s
appendFooter(stringBuffer);

// 好
stringBuffer.appendFooter();
```

如果函数必须修改某个状态，宁可修改它所属的对象的状态。

## 9. 无副作用

副作用是谎言——名字承诺了一件事，函数偷偷干了别的：

```text
// 名字说是检查用户名密码，却顺手初始化了 Session：
checkPassword(userName, password);   // 内部偷偷 Session.initialize()
```

要么把副作用写进名字（并接受它做两件事），要么去掉副作用。隐式的时序耦合尤其危险（必须先 `initialize()` 再其他操作），需要靠注释或结构暴露这种依赖。

## 10. 分隔指令与询问（Command Query Separation）

函数要么做事，要么回答问题，别两者都干：

```text
// 差：set 存在才设置，返回 true/false——读起来像 "attribute == "location""
if (set("username", "unclebob")) ...

// 好：指令与询问分开
if (attributeExists("username")) {
    setAttribute("username", "unclebob");
}
```

## 11. 结构化编程

- Dijkstra 主张单入单出。对小函数而言，提前 `return`、`break`、`continue` 无伤大雅，反而让卫语句更清晰。
- 对大函数而言，遵循单一出口才能收益；而大函数本身就该被拆掉。
- 所以真正的答案是：**先把函数变小**，规则自然松绑。

## 自查清单

- [ ] 这个函数能用一句话说清吗？（说清的话是这句话吗）
- [ ] 函数体的各行是否处于同一抽象层级？
- [ ] 有没有布尔参数？有两个以上参数吗？
- [ ] 调用这个函数的人，会不会被它的隐藏行为惊讶到？
- [ ] 我是不是又能从中提出一个独立的函数来？
